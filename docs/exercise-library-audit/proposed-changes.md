## 3. Deduplication (hard requirement — Phase 3 / 16)
Method: `scripts/exercise-audit/normalize.mjs` — lowercase → strip punctuation →
expand abbreviations (`db→dumbbell`, `bb→barbell`, `ohp→overhead press`,
`rdl→romanian deadlift`, `bw→bodyweight`, `single-arm→single arm`, …) → drop filler →
singularize → **sorted token set**. Two names are the same movement when: identical
normalized form, OR identical `(normalized-name, primary_muscle, equipment-class)`
signature, OR one token-set is a subset of the other **and every extra token is a mere
muscle-name restatement** (`biceps`, `chest`, …) — so "Dumbbell Bicep Curl" ≡
"Dumbbell Curl", but "Single-Leg Press" ≠ "Leg Press" and "Trap-Bar Deadlift" ≠
"Deadlift".
Result: **no new row duplicates an existing canonical movement.** Aliases are only ever
written to `exercise_aliases`, never as `exercise_library` rows, so search returns one
canonical row per movement by construction.

## 6. Schema DDL (additive, nullable, idempotent — via the existing `init-db.js` pattern)

```sql
-- exercise_library: 5 new nullable columns (no default that changes existing reads)
ALTER TABLE exercise_library ADD COLUMN compound_or_isolation TEXT;   -- 'compound' | 'isolation'
ALTER TABLE exercise_library ADD COLUMN is_unilateral        INTEGER; -- 0 | 1
ALTER TABLE exercise_library ADD COLUMN is_bodyweight        INTEGER; -- 0 | 1
ALTER TABLE exercise_library ADD COLUMN tracking_type        TEXT;    -- weight_reps | bodyweight_reps | weighted_bodyweight | time | distance_time
ALTER TABLE exercise_library ADD COLUMN default_reps         TEXT;    -- '8-12' | '30-45 sec'

CREATE TABLE IF NOT EXISTS exercise_relations (
  id          TEXT PRIMARY KEY,
  exercise_id TEXT NOT NULL REFERENCES exercise_library(id) ON DELETE CASCADE,
  related_id  TEXT NOT NULL REFERENCES exercise_library(id) ON DELETE CASCADE,
  relation    TEXT NOT NULL CHECK (relation IN ('alternative','progression','regression')),
  UNIQUE (exercise_id, related_id, relation)
);
CREATE INDEX IF NOT EXISTS idx_exrel_ex ON exercise_relations(exercise_id, relation);
```
Mirrored into `database/schema.sql` for fresh installs. The `ALTER`s go into the
`ADD_COLUMNS` tuple list in `backend/scripts/init-db.js` (SQLite guarded + PG path), the
`CREATE TABLE` into its migration block — exactly like the `foods` / `workouts` columns
already there.

### ⚠ One behavioural nuance to confirm
`backend/src/routes/me.js:894` (`POST /me/workouts`) reads `ex.reps ?? lib.default_reps ?? 10`.
The frontend picker **always sends `reps`**, so populating `default_reps` is inert for
every real caller. The only change: a hypothetical API call that omits `reps` would get
the library default (e.g. `"8-12"`) instead of `"10"`. If you'd rather keep existing
rows byte-identical, we populate `default_reps` for the **80 new rows only** and leave
the 207 existing rows `NULL`. Say which you prefer.
