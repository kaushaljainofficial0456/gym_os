# Training-Data Export Contract (backend → ML training pipeline)

**Owner (backend):** Kaushal. **Consumer (ML):** Sambhav.
Generated by the backend from **existing production data only** — the export never
writes to PostgreSQL, never invents data, and never changes the calorie contract.

The export is the bridge between the running system and Sambhav's training pipeline:

```
workouts → exercise_set_logs → client/profile → exercise_library
        └──> buildWorkoutCalorieInput (the single v0.2 feature choke point)
                └──> JSONL dataset (features + provenance + reserved label slot)
```

Because every record's `features` object is produced by the exact same
`buildWorkoutCalorieInput()` that the running routes use, the dataset is guaranteed
to match the v0.2 contract **by construction** — there is no second, driftable copy
of the feature logic.

---

## 1. How to generate

```bash
# Uses the configured database (DATABASE_URL in staging/prod, SQLite in dev).
cd backend
node scripts/export-training-data.js --out ../data/exports/calories.jsonl
```

- Writes **JSONL** — one record per completed workout with ≥ 1 real completed set.
- Without `--out`, records stream to stdout (summary always goes to stderr, counts
  only — never payloads).
- `--limit n` sets the page size for the batched read (default 100).
- Output directories are gitignored (`backend/data/exports/`) — datasets are
  generated artifacts, never committed.

### 1.1 Database access & RLS

The export uses the **standard application connection** (`getDb()` → `DATABASE_URL`).
RLS policies deliberately allow all rows on plain (non-transactional) reads — that
is the documented design in `database/rls.sql` ("when `app.org_id` is NOT set, all
rows are visible; the app SQL filters by org"). A training dataset is intentionally
cross-org, so no `SET LOCAL app.org_id` is issued and **no RLS or role change is
required**. If an ops deployment ever tightens the unset-org policy, re-run the
export with a read-elevated connection instead of changing application code.

## 2. Record schema (one JSON object per line)

```jsonc
{
  "schema_version": "0.2",        // calorie contract version of the features
  "workout_id": "wko_abc",        // opaque app token (join key, not PII)
  "client_id": "c_xyz",           // opaque app token — repeated measures key
  "org_id": "o_1",                // opaque tenant token
  "completed_at": "2026-08-15T10:00:00Z",
  "scheduled_date": "2026-08-15",
  "duration_measured": true,      // true only when started_at + completed_at exist
  "synthesized_sets_excluded": 0, // count of is_synthesized=1 sets dropped

  "features": {                   // EXACT contract 0.2 input — see
    //  ...                       //   docs/calorie-model-contract.md §2
    //  user / session / exercises
  },

  "label": {                      // reserved label slot — see §4
    "kcal": null,                 // NEVER fabricated
    "source": null,               // null today (no ground-truth source)
    "ground_truth": false
  },

  "baseline_estimate": {          // the persisted estimate at completion time
    "kcal": 285,                  //   (MET heuristic output — NOT ground truth)
    "model_version": "skos-cal-baseline-v1",
    "provider": "baseline"        // baseline | mock | ml
  }                               // null when no estimate was persisted
}
```

### 2.1 `features` — the v0.2 contract payload

`features` is byte-for-byte the output of `buildWorkoutCalorieInput()` and contains
exactly the fields defined in `docs/calorie-model-contract.md` §2:

- `features.user` — `age_years`, `sex`, `height_cm`, `body_weight_kg`
  (body weight resolved via the documented preference order: nearest `weight_logs`
  at/before the session day → `clients.current_weight` → `start_weight` →
  `target_weight` → `null`).
- `features.session` — `workout_id`, `duration_seconds`, `duration_minutes`,
  `intensity_rating`, `exercise_count`, `total_sets`, `total_reps`,
  `total_volume_kg`, `volume_per_minute`, `sets_per_minute`, `reps_per_minute`,
  `relative_load`, `compound_set_ratio`, `isolation_set_ratio`.
- `features.exercises[]` — per-exercise `exercise_id`, `exercise_type`,
  `muscle_group`, `equipment`, `movement_pattern`, `compound_or_isolation`,
  `completed_sets[]` (per-set `set_number`, `reps`, `weight_kg`, `rir`,
  `rest_seconds`, `completed: 1`) plus the v0.2 per-exercise aggregates `sets`,
  `total_reps`, `total_volume_kg`, `average_load_kg`.

The backend contract is the **only** definition of these fields. Do not re-derive
or re-name them in the training pipeline.

## 3. Filtering rules (baked into the generator)

| Rule | Behavior |
|---|---|
| Completed sessions only | `workouts.status = 'completed'` and `completed_at` present |
| Actual completed sets only | `exercise_set_logs.completed ≠ 0` — incomplete/skipped sets are never features |
| Synthesized legacy data excluded | `is_synthesized = 1` rows are dropped **before** aggregation and counted in `synthesized_sets_excluded`; they never contribute workload |
| Zero-real-set workouts excluded | a workout whose real completed sets total 0 produces **no record** (nothing usable to train on) |
| Skipped exercises | appear in `features.exercises[]` with `completed_sets: []` and 0 aggregates — they contribute 0 sets/0 reps/0 volume to `features.session` |
| Ambiguous name-only attribution | if a workout has multiple name-only exercises (`exercise_id IS NULL`) their sets cannot be re-attributed from the DB — the workout is skipped and counted in the CLI summary |
| Duplicate library exercises | if the same library exercise appears twice in one workout, its sets collapse into a single per-exercise entry (session totals are unaffected) |

## 4. Label availability — READ BEFORE TRAINING

**There is currently no reliable calorie ground-truth label.** The persisted
`workouts.estimated_active_kcal` is the output of the deterministic **baseline MET
heuristic** (or `mock`), not a measured expenditure. Training a supervised model
against it would teach the model to reproduce the heuristic — that is why the
`label.kcal` slot is `null` and the persisted estimate is surfaced separately as
`baseline_estimate` (for baseline comparison / sanity checks only).

- **Do not** treat `baseline_estimate.kcal` as a training label.
- When a real label source is agreed (e.g. validated expenditure measurements or a
  curated hand-labeled set), it slots into `label.kcal` / `label.source` with
  `ground_truth: true`. The record format is ready; no contract change is needed
  to consume it.
- `features` are complete today — training on features can start immediately
  (unsupervised/pre-training, baseline comparisons, or downstream tasks).

## 5. Duration semantics

- `features.session.duration_seconds` / `duration_minutes` carry **measured
  duration only** (`completed_at − started_at`, server-authoritative). When no
  `started_at` exists (e.g. NL-logged sessions via `/intel/confirm-workout`),
  both are `null` and `duration_measured` is `false`.
- The baseline provider's internal `estimateDurationMinutes()` is **never** written
  into `features` — treat `null` as "no measured duration", never `0`, never an
  estimate.

## 6. PII & security rules

- The export contains **no names, emails, phones, notes, instructions, photos,
  body measurements beyond the contract features, or credential material.**
- `workout_id` / `client_id` / `org_id` are opaque app-generated tokens; they are
  included because repeated measures per client are useful and they are not
  personal data. Treat the dataset as sensitive anyway (defense in depth).
- The CLI logs **counts only** — never payloads, never raw set data, never body
  weight. Any per-workout failure is logged with the opaque workout id and a
  truncated error message only.
- Units are contract units throughout: `kg`, `seconds`/`minutes`, `kcal`.

## 7. Versioning

- `schema_version` mirrors the calorie contract (currently `0.2`). Bumping the
  calorie contract to `0.3` requires regenerating datasets and re-filtering on the
  new version — coordinate with Kaushal before training on a new version.
- Dataset format changes (provenance/label fields) are documented here; feature
  field changes only happen via `docs/calorie-model-contract.md`.
